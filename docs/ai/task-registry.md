### TASK-031: Persistent Desktop Shell Navigation

Status: Started. Replace document-level sidebar navigation with one Electron renderer shell, internal History API routes and explicit view lifecycles. This is a desktop-app migration, not a cosmetic SPA overlay.
Priority: High.
Risk: High because Flow Map and Workspace own live runtimes, workers, listeners and unsaved UI state that must not be duplicated, leaked or silently reset.

Current sub-steps:

- Navigation contract: internal routes use the History API and an explicit `mount` / `dispose` lifecycle; unregistered URLs remain temporary legacy document routes during the migration.
- Navigation fallback regression: fixed. `TrackerLensSidebar.navigate()` now returns a handled result after starting an internal route; callers using the legacy fallback idiom no longer execute `window.location.assign()` immediately afterward. `test/tl-sidebar-navigation.test.cjs` preserves this contract.
- First vertical slice: in progress. `app.html` is now Electron's default entry point; Library, Library Flow Map, Workspace Editor, Settings, AI Runtime Center, Runtime Python e Modelli, Statistics, Connections, DevTools, Profile, Database Explorer and Flow Map render inside its stable sidebar/outlet without document navigation. The router normalizes Electron `file://` absolute paths to logical routes, and each migrated view disconnects its local observers/subscriptions/timers before unmounting. Workspace also attaches its keyboard/pointer document handlers only while active and removes them on exit. Contextual jumps from Flow Map to AI, DevTools, Connections and Library Flow Map use that same internal navigation contract.
- Compatibility: retain current HTML URLs as temporary entry points and map them to their equivalent internal route during the phased migration.
- Runtime-view safety: Workspace has explicit listener ownership. Flow Map now has explicit lifecycle ownership; interactive QA must still prove that stop/start duplicates neither a runtime owner nor an active Live Test, and that the canvas recovers correctly.
- Flow Map lifecycle foundation: implemented in `js/flowMapView.js`. Its bootstrap exposes `TrackerLensFlowMapLifecycle.start/stop/status`, tracks the worker subscription, polling timer and Flow-specific global listeners, disconnects the live Event Bus listener and removes page-level listeners on stop. Flow Map is registered in `app.html` and starts only when its internal route is mounted. Next is interactive QA that proves a stop/start leaves exactly one runtime owner and no active Live Test orphaned.

### TASK-029: Custom Node Packages

Status: Started. Phase 1 defines `.tl-node.zip` as the portable artifact and implements the Core-owned manifest-only import contract; package runtime execution remains blocked.
Priority: High.
Risk: High because external JavaScript cannot be fully controlled; TL must distinguish verified marketplace packages from unverified local/external installs.

Current sub-steps:

- Package contract: in progress. `.tl-node.zip` contains `node.json`, optional `runtime.js`, `ui.json`, `assets/`, `schemas/`, `examples/` and `README.md`; Core records archive hash/provenance in `tl_packages`, while Flow Maps retain only package references/configuration.
- Manifest-only import: in progress. Core validates and copies the archive into app data, catalogs metadata/assets/UI schema and registers a disabled palette entry without executing package JS or revealing filesystem paths to the renderer.
- Manifest-only backend: implemented. `CustomNodePackageManager` parses `.tl-node.zip` centrally (including traversal/encryption/compression checks), validates root `node.json`, copies the exact archive by SHA-256 into Core-owned app data and writes an opaque `tl_packages` record with `installState=manifest-only` and `runtimeExecution=blocked`. The validated preload bridge exposes inspect/install/list only; palette UI registration and the explicit install-review dialog are the next Phase 1 work.
- Manifest-only CMSwift import and palette registration: implemented. Flow Map exposes `Custom Nodes`; it opens the native archive picker through the restricted bridge, renders a manifest/permission/trust/SHA-256 review before a separate explicit import confirmation, and lists installed packages. Imported packages appear under `Custom Packages`, retain only their declared ports/reference and are insertable as visibly disabled manifest-only nodes. It never receives a filesystem path, cannot live-test the node and labels every package `Runtime: blocked`.
- Import-time static audit: implemented. Before Core copies an archive, it reads the declared `runtime.js` only as text and catalogs transparent findings for dynamic code, process/module loading, direct network/filesystem/browser storage access and undeclared permission mismatches. This is explicitly a review aid, not an execution permit or a safety guarantee; runtime remains blocked.
- Sandbox protocol foundation: implemented as `tl-custom-node-sandbox/v1`. Core-to-runner messages use only opaque package identity/hash plus inputs/config/context and the intersection of declared and explicitly granted permissions. Runner messages are limited to ready, declared-port emits, logs, brokered tool calls and results; Core validates every port and capability. Manifest-only packages remain non-executable. The disposable Electron runner and Core broker are the next high-risk implementation slice; Node `vm`, child processes and utility processes are not accepted as isolation boundaries.
- Permission-consent foundation: implemented. `tl_packages` now stores manifest declarations separately from a zero-default Core-owned grant record. A confirmed grant is bound to package id/version/archive SHA-256, is intersected with the manifest and therefore cannot expand package authority. The renderer can inspect consent state but cannot bypass Core confirmation; recording consent does not unblock execution.
- Sandbox broker foundation: implemented. Core owns `CustomNodeSandboxBroker`, which creates only catalog-validated requests, revalidates every untrusted runner message, preserves a per-run event trace and rejects any message after completion. The disposable Electron runner is not connected yet; package JavaScript remains non-executable.
- Sandbox terminal-result contract: implemented. A runner must terminate with an explicit `success` or `failed` result; Core permits one waiter per execution and resolves it only from the validated terminal event or a Core-recorded runner failure. This is the prerequisite for forwarding sandbox `emit` events to Flow Map without racing an incomplete run.
- Flow Map sandbox bridge: implemented but unreachable for manifest-only imports. Under the feature flag, the restricted renderer API submits identity/inputs/config/context/timeout only; Core returns a bounded terminal result and broker-validated `emit`/`log` trace only. Processor Runtime re-emits valid package ports to the Flow Map bus with execution provenance. No runtime source, package path or unrestricted IPC reaches the renderer. The explicit activation lifecycle that could change a catalog record to `sandboxed` is the next gate.
- Sandbox activation gate: implemented. The Core catalog accepts `runtimeExecution=sandboxed` only after separate declared-permission consent and an explicit CMS activation confirmation, tied to package id/version/archive SHA-256. The Custom Nodes review surface shows the experimental activation warning and the palette reflects the resulting `sandbox-ready` state. The feature flag remains a further Core-owned gate, so an activated record still cannot execute when sandbox support is disabled.
- Electron end-to-end sandbox verification: implemented as `npm run test:custom-node-sandbox`. It launches the real trusted runner/preload in a disposable Electron window with an unprivileged fixture module, then asserts that a declared output `emit` and log reach the Core broker. This validates the actual renderer-to-Main sender binding path without importing or executing a user archive.
- Tool broker protocol foundation: implemented. The runner provides narrow AI/memory/runtime-graph wrappers only; every call carries a required `callId`, is sender-bound in Main and is revalidated by `CustomNodeSandboxBroker` before it reaches an optional Core dispatcher. No dispatcher is installed by default, so no package gains a capability merely from declaring/granting it. The next slice is a read-only Core-owned dispatcher, beginning with a scoped runtime-graph read; mutation remains preflight-only.
- Read-only graph dispatcher: implemented. When—and only when—the disabled-by-default sandbox feature flag is enabled, Core registers `runtimeGraph.read` against the execution request’s workspace scope. It returns full nodes/dependencies/channels from the allow-listed persistence boundary with provenance but without SQLite paths/handles or mutation APIs. `runtimeGraph.preflight` returns an explicitly non-executable proposal; no graph write dispatcher exists.
- Safe-executor preflight proposal: implemented without a write path. `runtimeGraph.preflight` recognizes only registered TL mutation tools, scopes the proposed action to the request workspace and reports affected dependencies for `deleteNode`. It returns `executable:false`; only a trusted TL surface can revalidate and send a separately confirmed action through the existing safe executor.
- User end-to-end package verification: completed. An explicitly activated local `Sample Text Inspector` package completed a Flow Map Live Test and emitted its declared `diagnostic` output with `runtimeResult` provenance and a test `runId`. `npm run dev` enables the experimental sandbox; no additional package capability was enabled by this change.
- Electron runner adapter: base implemented. Behind `TL_ENABLE_CUSTOM_NODE_SANDBOX=1`, it configures a disposable BrowserWindow with an isolated session, Chromium sandbox, context isolation, disabled Node integration, denied navigation/popups, denied browser permissions and denied HTTP(S)/WebSocket traffic. Its Main IPC route resolves the execution from the sender `webContents`, so package-provided messages cannot select another run. Core-only archive-source loading now accepts only a unique, explicitly sandbox-enabled catalog record and rechecks archive hash, manifest identity/mode and bounded runtime size before Main can launch it; source never crosses the renderer boundary. Flow Map/Runtime Manager feature-gated execution wiring remains pending; no package code runs yet.
- Permission model: planned. Packages must declare network, filesystem, AI provider, memory and runtime graph permissions; TL must show requested permissions before install.
- Trust levels: planned. Nodes should be visibly marked as `verified`, `community`, `local-dev` or `blocked`.
- Official marketplace: planned. Verified packages require signature checks, manifest validation, static analysis, AI-assisted code review, smoke tests and a verified badge.
- External/local install: planned. Users may install local zip/folder packages only with explicit warning; unverified code is user-risk and must not be presented as TL-verified.
- Sandboxed runtime: planned after manifest-only import. Runtime JS should run through a restricted `{ input, config, tools, emit, log }` API, with AI/memory/network/runtime graph access gated by permissions.
- Versioning/migrations: planned. Package updates must preserve existing Flow Map node configs and provide migration hooks before marketplace rollout.
